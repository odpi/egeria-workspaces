# Documentation surfaces to check on every command change

None of these are regenerated by `refresh_specs` — they're hand-maintained
prose that references the family/command surface and will silently drift
unless checked against the actual diff every time. Treat "update docs" as a
required step of the lifecycle, not an afterthought — go through this list
every time, not just when something reminds you to.

For each, the useful check is: **did this change add, remove, or rename a
family or command that this doc mentions by name?** If yes, edit it now
(these are plain text edits — reversible, low-risk, fine to make directly and
let the user review via `git diff`). If a doc's content is unaffected by the
specific change, say so explicitly rather than skipping it silently, so the
user knows it was checked and not just missed.

## egeria-python

| File | What in it tracks the command surface |
|---|---|
| `docs/dr_egeria_manual.md` | "Supported Command Families" section — prose list of families with example commands per family |
| `CLAUDE.md` | Dispatcher registration notes, `COLLECTION_SUBTYPES`/`PROJECT_SUBTYPES` mentions — check if a new type needs adding to these lists (this is also a *code* change, not just docs — see CLAUDE.md's "Adding a new processor" steps) |
| `AGENTS.md` | Deeper architecture map — check for family-specific detail that might reference removed/renamed commands |
| `md_processing/data/compact_commands/README.md` | Compact JSON schema doc — only needs updating if the *schema itself* changes (new field in `attribute_definitions`/`bundles`/`commands`), not for ordinary command additions |

## egeria-workspaces-fs

| File | What in it tracks the command surface |
|---|---|
| `portal-docs/tools/dr-egeria/templates-basic.md` | Curated example commands grouped by family heading (Glossary, Governance, Feedback, ...) — needs a new section if a family is added, needs pruning if a shown example command is renamed/removed |
| `portal-docs/tools/dr-egeria/templates-advanced.md` | Same, for advanced-level families (Information Supply Chains, Data Design, ...) |
| `portal-docs/tools/dr-egeria/overview.md` | Conceptual/architecture doc, not family-specific — rarely needs touching for a command change |

## egeria-advisor

Docs here (`docs/PROJECT_SUMMARY.md`, `docs/literate-governance-plan.md`,
`docs/design/SCOPED_QUERIES_IMPLEMENTATION.md`) are planning/design
documents that happen to mention family names as examples — check if the
specific change is relevant to what they're discussing, but these are lower
priority than the portal-docs above since they document design intent, not
the current command surface as a reference.

## Inside Tinderbox itself

**Retired 2026-08-05 — no longer part of this checklist.** Tinderbox is no
longer maintained; its in-document READMEs (structure/process guides,
per-family "Bundle Reference Guide" notes) are not part of the active
documentation surface anymore and don't need checking on a command change.
