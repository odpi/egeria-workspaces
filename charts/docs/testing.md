# Testing and changing the charts (contributors)

This page is for people who change the charts. Users start at [../README.md](../README.md).

## Rules

- **Compose is the source of truth.** The charts copy compose's configuration into `files/`. Nothing under
  `compose-configs/` changes for the charts. `tests/drift_test.py` fails when the two disagree.
- The Portal's `httpd.conf` and proxy routes are compose's, regenerated by `tests/gen_portal_conf.py` (which
  `drift_test.py` runs in `--check` mode). The vhost is the chart's: plain HTTP on 8085, with the SSL lines removed.
  Routes to services the chart does not deploy (My Profile, Trellis) stay in the config and answer 503.
- `EGERIA_ROOT_PATH` is `/app/dr-egeria`, never compose's `/` (a non-root user cannot write there).
  `portal_render_test.py` checks it.
- Every object name comes from the release name; nothing is cluster-scoped.
- The production posture must never render the tracked demo files (`render_test.py`).
  `egeria-stack/files/demo-keystore-password` is the public demo keystore password, kept only so the chart can
  recognise and refuse it. `drift_test.py` checks it against the properties files; `stack_render_test.py` checks it
  never appears in a production manifest, and in a demo one only inside the platform's demo TLS Secret.

## Offline checks (no cluster)

Run these before every push, from the repository root:

```bash
for c in egeria-platform egeria-portal egeria-stack; do helm dependency build charts/$c; done
for c in egeria-common egeria-demo-postgres egeria-demo-kafka egeria-platform; do helm lint --strict charts/$c; done
helm lint --strict charts/egeria-portal -f charts/egeria-portal/ci/lint-values.yaml
helm lint --strict charts/egeria-stack -f charts/egeria-stack/ci/lint-values.yaml
python3 charts/tests/drift_test.py                  # compose <-> chart drift
python3 charts/tests/render_test.py                 # platform render tests
python3 charts/tests/portal_render_test.py          # Portal render tests
python3 charts/tests/stack_render_test.py           # umbrella render tests
ct lint --config charts/ct.yaml --all               # chart-testing lint (ct.yaml, ct/)
HELM=helm3 python3 charts/tests/render_test.py      # the same on Helm 3 (also drift_test.py)
```

`helm lint` prints `funcMap fail` INFO lines for the platform chart (it renders without the required values); only
the final `0 chart(s) failed` line matters.

## Test scripts

| Script | What it does | Ran on |
|---|---|---|
| `tests/drift_test.py` | Compose vs chart: images, properties, server configs, Postgres set-up, Portal config, the demo keystore password | offline |
| `tests/render_test.py`, `portal_render_test.py`, `stack_render_test.py` | `helm template` checks for each chart: refusals, postures, security contexts, PO-68 canary | offline |
| `tests/gen_portal_conf.py` | Regenerates the Portal's Apache files from compose | offline |
| `tests/proof112a.sh [build]` | Builds (with `build`) and proves the Portal and Apache images: default user and an arbitrary UID with GID 0, read-only content mounts, health route, writable paths; compose config unchanged | Docker |
| `tests/proof112c.sh <env>` | The platform image under an arbitrary UID with GID 0 against a private Postgres and Kafka | Docker |
| `tests/kind_infra.sh <ns>` | A test Postgres (`postgres:5442`) and Kafka (`kafka.<ns>.svc.cluster.local:9192`) in a namespace. Not part of any chart. | kind, crc |
| `tests/kind_install.sh <env> <ns> [release]` | `egeria-platform` alone, timed. `MODE=production` makes its own keystore and Secrets; `BUNDLED=1` uses the demo subcharts; `HELM=helm3` | kind |
| `tests/kind_stack_prod.sh <ns> [release]` | Production-style `egeria-stack` (freshstart) with external test infra, own SAN keystore, existing Secrets, digests, NetworkPolicies | kind |
| `tests/make_san_keystore.sh <out> <ns> <svc> [alias]` | A throwaway CA (3 days) and a keystore and truststore with SANs for the Service names and random passwords | used by the above |
| `tests/crc_stack.sh [ns] [release]` | Demo `egeria-stack` with `global.openshift=true` on OpenShift Local; infra in `<ns>-infra` under `anyuid`. `ENVIRONMENT=quickstart DEMO_MODE=true` for demoMode. | crc |
| `tests/crc_stack_prod.sh [ns] [release]` | Production-style stack on OpenShift Local, images pushed to the internal registry. Keeps its Secrets on a re-run. | crc |
| `tests/kind_trusted_proxies.sh <ns> [release]` | PO-83: the Portal's sign-in rate limit counts per real client IP when `PORTAL_TRUSTED_PROXIES` names the Apache headless Service, shares one budget when it does not, and port 8000 is reachable only through Apache | kind |
| `tests/kind_re.sh <ns> [release]` | `trellis-re` (Resource Explorer) on a quickstart platform with the test Postgres: owner role for the schema Job, runtime role for the pods | kind |
| `tests/kind_stack_re_ingress.sh <ns> [release]` | A freshstart demo stack with `re.enabled` and the Portal behind ingress-nginx: helm test (with the PO-78 canary step), anonymous 401 and 302, signed-in 200. Needs the refusal-lift branch too | kind |
| `tests/crc_re.sh [ns] [release]` | `trellis-re` in the production posture on OpenShift Local (restricted-v2, image by digest from the internal registry, own SAN keystore, tls.verify, NetworkPolicies, owner/runtime roles); one platform at a time, so scale other platform releases to zero first | crc |
| `tests/crc_route.sh [ns] [release] [host]` | Adds an edge Route (from the chart's Ingress) to an installed stack and checks it from the host | crc |

`kind_install.sh` expects a running kind cluster. Do not preload images with `kind load` on a Docker that uses the
containerd image store. For the Portal images, connect a local registry to kind's network
(`docker network connect kind <registry>`) and add a `hosts.toml` for it on the node.

  `helm test` passed for both.

  (UID 1000730000, GID 0), 5/5 servers, both canaries passed including the PO-68 check.

Found on the way: current Portal images keep the demo sign-in in Postgres (`DEMO_DB_*`), not SQLite, so the chart's `DEMO_DB_PATH` is stale (the sign-in answered 500 until the script gave the Portal a database). (This predates TR-134: the chart now sets DEMO_DB_PATH to SQLite at /app/demo-data/demo.db, and demoMode needs a Portal image with the TR-134 change.)
- Resource Explorer (`kind_re.sh`, trellis `efd55108`): the schema Job (owner role) printed `schema ready`, a second `helm upgrade` ran it again with the same line, the pods ran `RE_SCHEMA_MODE=external` as a role that cannot create anything (`permission denied for schema`) and has DML on every table the owner made, six marker rows were written, and `helm test` passed (`/health/ready` 200, a protected API 401). An unapplied schema is refused with `SchemaNotReady`. Not run in demo: see the production line below.
- Resource Explorer, production posture (`MODE=production kind_re.sh`): image pinned by digest, existing Secrets, `tls.verify=true` with the platform's CA (the worker reaches the platform with the CA and is refused without it), NetworkPolicies for web and worker (a pod without the platform client label cannot reach the platform), a separate owner role, no owner credentials in any pod, an Ingress with TLS (`/health/ready` 200, `/api/projects` 401), the schema Job again on `helm upgrade`, `helm test` passed. Not run: OpenShift, the Prefect worker.
- Resource Explorer with the A2A role (`A2A=1 MODE=production kind_re.sh`, trellis `73b5bfcc`): `helm test` checked `/health`, the public `agents.json` (200) and that an anonymous agent call gets 401 with a `WWW-Authenticate: Bearer` challenge; with a raw Egeria token (obtained over verified TLS) `/whoami` answered 200 as that user, a bogus token 401; a task that does not exist and a message into a task that is gone both answer 404 with words (no 500); the A2A pod has `PORT=8100`, `A2A_ALLOW_ANONYMOUS=false`, the in-cluster `A2A_PUBLIC_URL` and no `RE_DAEMON_*`. That image's index still carried an `egeria` block with the internal platform URL: TR-133 removes it (separate trellis branch). Not run: A2A through an Ingress (none is built), more than one replica (refused).
- Resource Explorer with the Prefect worker (`PREFECT=1 MODE=production kind_re.sh`, trellis `73b5bfcc`, a test Prefect server from the RE image): the init step made the `process` pool, the worker deployed `re-survey-step-73b5bfcc` on queue `re-73b5bfcc` and was ONLINE, `helm test` waited for it, and a dispatched step (`repo_homepage` on a repo) COMPLETED on the worker, writing its result to the registry as the runtime role. Not run: Prefect on OpenShift, a Prefect server you operate (the chart does not run one).
- Resource Explorer on OpenShift Local (`crc_re.sh`, production posture): restricted-v2 with an assigned UID and GID 0, image by digest, `helm test` passed, the runtime role denied CREATE, a pod without the platform client label cannot reach the platform, `tls.verify` works with the platform CA. It found two OpenShift-only defects that kind (UID 1000) hid: pyegeria's relative `logs` directory under a root-owned `/app` (fixed in the chart: `logs.directory`) and the Dr.Egeria docs tree being `trellis:trellis` (fixed in the image, trellis `64e3007c`); after both, the bootstrap heal ran (`survey-definitions healed`). Also live: a project added with a new homepage host is refused until `helm upgrade` runs the schema Job, then its `web_docs_<host>` collection accepts an insert and an undeclared host is still refused (TR-129, TR-130).
- Route (`crc_route.sh`) on the demoMode stack: `/portal` 302, `/login` 200, `POST {}` to `/api/egeria-token` 401, an
  authenticated API 401 for an anonymous caller, http redirected to an `https://` location, `helm test` passed.

**Not run:** demoMode on kind; a Route on the production-style stack or with its own certificate; a full OpenShift
cluster; the optional Portal content claims; sharing exchange claims between the platform and the Portal.

**TR-123, render-tested only:** `imagePullSecrets`, `global.imagePullSecrets` and `serviceAccountName` on every pod;
`portal.platform.userDirectorySecret` (now required for a production freshstart Portal, and set by `kind_stack_prod.sh`
and `crc_stack_prod.sh`, which have not been re-run with it); Portal and Apache probe timings from values; Apache
tolerations and affinity; the platform image reference without a digest. A cray run on kind and OpenShift Local should
re-run `kind_stack_prod.sh`, `crc_stack.sh`, `crc_stack_prod.sh` and `crc_route.sh` to prove them.

The canary account and the Portal's Egeria user in the production-style runs used the public demo user-directory
passwords. Those runs prove the wiring, not production credential hygiene.
