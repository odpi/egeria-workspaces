# Portal startup and initialization

How the Portal comes up, in order, and — the part that actually needed
writing down — how it notices Egeria data is missing (a wipe, a fresh
deploy, a demo reset) and re-seeds itself. Covers both `egeria-quickstart`
and `egeria-freshstart`; differences are called out explicitly.

## 1. Container startup order

`docker compose up` for `egeria-quickstart.yaml`:

- `egeria-main` (the Egeria platform) starts first in wall-clock terms, but
  **`pyegeria-web`'s `depends_on: [egeria-main]` has no `condition:`**, which
  defaults to `service_started` — Compose only waits for the container
  *process* to start, not for its healthcheck
  (`.../server-platform/origin`, `start_period: 60s`, up to 15 retries) to
  pass. In practice **`pyegeria-web` starts running well before Egeria is
  actually ready to serve requests.** This matters for §3 below.
- `apache-web` depends on `pyegeria-web` (proxies `/api` to it).
- `obsidian-quickstart` depends on `pyegeria-web` with
  `condition: service_healthy` — the one place in the stack that actually
  waits.
- `egeria-watchdog` has no dependency; it just watches the `egeria-main`
  container via the Docker socket and alerts on a crash/OOM-kill.

Freshstart's compose file (`egeria-freshstart.yaml`) has the equivalent
shape; see it directly for its own service names.

## 2. FastAPI process startup (`pyegeria_handler.py`)

Two phases, both in `pyegeria_handler.py`:

1. **`_bootstrap_runtime_defaults()`** — runs at import time, before the
   FastAPI app object even exists. Sets `EGERIA_USER`/`EGERIA_USER_PASSWORD`
   defaults, creates the log directory, and picks `EGERIA_ROOT_PATH` /
   `EGERIA_INBOX_PATH` / `EGERIA_OUTBOX_PATH` based on whether it's running
   inside a container (`/.dockerenv` present) or on a host checkout.

2. **`_lifespan(app)`** — a FastAPI `lifespan` context manager, starts every
   background scheduler in order on startup and stops them in reverse order
   on shutdown:

   ```
   obsidian_lock_handler.start_scheduler()   # single-writer lock on the Obsidian vault
   jupyter_lock_handler.start_scheduler()    # same idea, for the Jupyter service
   advisor_lock_handler.start_scheduler()    # reservation lock for the Egeria Advisor service
   bootstrap_monitor_handler.start_scheduler()  # data-initialization auto-heal — see §3
   demo_reset_handler.start_scheduler()      # DEMO_MODE only — scheduled full-stack reset
   ```

   (Freshstart's `_lifespan` is the same shape minus `advisor_lock_handler`
   and `demo_reset_handler` — DEMO_MODE is always false there.)

   None of these block app startup on failure — each `start_scheduler()` is
   independent, and `bootstrap_monitor_handler`'s specifically swallows and
   logs any error from its first check (see §3.4).

## 3. Data initialization ("bootstrap")

The problem: the Egeria metadata store gets wiped sometimes (a fresh
deploy, a manual DB drop, DEMO_MODE's own scheduled reset), and Egeria
itself has no "was I just reset" signal. Several Portal features
(Overview's Governance Metrics, Local Dashboards, and anything else an
admin registers) depend on specific elements existing, seeded by
Dr.Egeria markdown documents. If nobody notices the wipe, those features
just render empty with no explanation.

### 3.1 What's discovered, and from where

`bootstrap_batches.py` scans `dr-egeria-inbox` (mounted `:ro` at
`/deployments/loading-bay/dr-egeria-inbox`) — **every subfolder is a
"batch"**, discovered automatically, no code change needed to add one.
A short, hand-maintained list in the same file
(`_EXTRA_BATCH_ROOTS`) additionally covers a couple of core-portal seed
docs that live alongside the handler code itself (generated by their own
scripts, e.g. `gen_governance_metrics.py` → `OVERVIEW_GOVERNANCE_METRICS.dr-egeria.md`)
rather than under the user-facing inbox tree.

An optional `_batch.json` in a folder gives it:
- `displayName` / `description` — cosmetic, shown in the admin panel.
- `files` — **explicit execution order** for that folder. Any `.md` file
  in the folder the list doesn't mention runs *after* the listed ones,
  alphabetically. No manifest at all → pure alphabetical order.
  (`_EXTRA_BATCH_ROOTS` folders are the one exception: their `files` list
  is used as-is, no auto-append, since that directory also holds
  unrelated source files — a manifest is *required* to register at all.)
- `canary` — `{"type": "<metadataElementTypeName>", "name": "<exact displayName>"}`.
  Presence/absence of this element is the reset-detection signal for the
  whole batch (see §3.2). No canary → the batch is manual/on-demand only,
  never auto-healed.
- `defaultEnabled` — `true` keeps a batch auto-healing out of the box on a
  fresh deploy, with no seed selection file needed.
- `idempotent` — `true` unless set explicitly (default `true`, so existing
  manifests are unaffected). Set `false` when a batch contains a command
  that creates a relationship/record with **no pre-existence check**, so
  re-running it against an already-seeded target duplicates it. This is a
  real, confirmed case, not a hypothetical: `Link Governance Results`
  (`md_processing/v2/governance.py`) calls `_async_link_governance_results`
  unconditionally — no dedup. (Contrast `Link Report to Dashboard Sheet`
  in `dashboard_sheet.py`, which matches on `ref == report_name` and
  replaces in place — genuinely idempotent despite looking like the same
  class of "Link" command; don't assume by verb, check the processor.)
  `overview-governance-metrics`'s manifest sets this `false`.
  Auto-heal is **unaffected** by this flag — it only ever runs a batch
  whose canary is missing, never a present one, so it can't hit this. It
  exists purely to gate the admin panel's manual "Run Now"/"Run All
  Enabled" actions, which run unconditionally otherwise: both
  `bootstrap_admin_handler.py` endpoints return `409` with an explanatory
  message unless the request passes `?confirm=true`, and both admin UIs
  show a `⚠ not safe to re-run` badge and a native `confirm()` prompt
  quoting the server's own message before retrying with that flag.

An optional top-level `dr-egeria-inbox/_folder_order.json` — a flat JSON
array of batch ids — controls the order *batches* run in relative to each
other, with the same "explicit list, then alphabetical remainder" rule.

Which batches/files are actually enabled is admin-editable state, stored
in `~/.pyegeria/bootstrap_batches.json` (env-overridable via
`PYEGERIA_BOOTSTRAP_STORE`) — a plain local file, not the `demo_auth`
Postgres table used elsewhere in this app for admin config, because
**freshstart has no Postgres wired up at all.** A batch/file with no saved
selection yet falls back to its manifest's `defaultEnabled` (false if
unset).

### 3.2 Detecting a reset

`bootstrap_monitor_handler.py`'s `_canary_present()` does one cheap bounded
lookup per batch that declares a canary: `FindRequestBody` with an exact
`displayName` EQ match, `graphQueryDepth: 0`, `pageSize: 1`. Found →
present, nothing to do. Missing → the batch gets healed.

This is presence detection only, **not staleness detection** — it can't
tell "exists but is out of date," only "exists" vs. "doesn't." That's
deliberate: every Dr.Egeria doc here is upsert-safe, so unconditionally
re-running is always correct, which made staleness diffing unnecessary
complexity.

`homeMetadataCollectionId` does **not** change across a real reset
(confirmed live) — it was an early candidate for the detection signal and
doesn't work; canary presence is the only reliable one found.

### 3.3 Healing (re-running the docs)

Each doc runs via `asyncio.create_subprocess_exec("dr_egeria", "--process", doc_path)`
— a subprocess to the CLI itself, executed from inside the same running
container process, so it always writes to the exact store this app reads
from (running `dr_egeria` from a different machine/venv against a
different server is the #1 way to make this silently not work).

Two different failure strategies, on purpose:
- **Auto-heal** (`_heal_family` in `bootstrap_monitor_handler.py`): stops
  at the first failing doc *within* a batch, since later docs in the same
  batch typically depend on earlier ones' output. Other batches still get
  processed independently.
- **Manual admin runs** (`run_batch`/`run_all_enabled` in
  `bootstrap_batches.py`, used by the admin panel's "Run Now" / "Run All
  Enabled" buttons): keeps going through every file regardless of earlier
  failures, and reports full per-file results — an admin who explicitly
  triggered a run wants complete visibility, not fail-fast.

### 3.4 When checks actually run, and failure handling

- **Startup**: `start_scheduler()` runs one `check_and_heal_all()` pass
  immediately (covers a redeploy, where the process restarts right
  alongside the reset), wrapped in try/except — a failure here is logged
  and swallowed, never blocks app startup.
  - **Startup fast-retry window** (fixed 2026-08-19): per §1, `pyegeria-web`
    can start before `egeria-main` is actually reachable, so this first
    check often fails open (see next bullet). Rather than then waiting the
    full `BOOTSTRAP_CHECK_INTERVAL_SECONDS` for the next real attempt,
    `start_scheduler()` opens a short window — `_monitor_loop` retries every
    `BOOTSTRAP_STARTUP_RETRY_SECONDS` (default 20s) instead of the normal
    interval, until either a check actually reaches Egeria or
    `BOOTSTRAP_STARTUP_RETRY_WINDOW_SECONDS` (default 300s / 5 min) elapses
    — then it settles into the normal cadence for good. Deliberately a
    one-shot window tied to process startup: a *later*, separate outage
    does not reopen it and just gets the normal gentle interval, so a
    genuine extended Egeria outage isn't hammered with retries forever.
    Chose this over changing `depends_on: egeria-main` to
    `condition: service_healthy` in the compose file — that would delay
    `pyegeria-web` (and everything behind it) by minutes on every cold
    start, and Egeria's healthcheck only confirms the platform origin
    endpoint responds, not that the specific view server
    (`EGERIA_VIEW_SERVER`) the canary lookups use has actually finished
    starting — a partial fix for a bigger cost.
- **Periodic**: every `BOOTSTRAP_CHECK_INTERVAL_SECONDS` (default 600s /
  10 min) after that, to also catch a reset where only the Egeria DB
  container was wiped without the web process restarting.
- **Egeria unreachable during a check**: the exception is caught and
  treated as **present** (fails open) — "connection failure isn't
  evidence of a reset." This avoids a false-positive heal storm every time
  Egeria is briefly unreachable, at the cost of the startup race above.
- **DEMO_MODE's own scheduled reset** (`demo_reset_handler.py`) does
  **not** call the bootstrap heal directly — there's no coupling between
  the two. Recovery after a demo reset relies entirely on the next
  periodic bootstrap check, i.e. there's a real window (up to 10 min by
  default) where demo data is missing after a scheduled reset. Worth
  tightening (have `demo_reset_handler` call
  `bootstrap_monitor_handler.check_and_heal_all()` directly after a
  reset) if that lag becomes a problem in practice — not done yet.
- **No distributed lock.** Nothing here guards against two processes (e.g.
  multiple replicas) independently detecting a reset and healing
  concurrently. Docs being upsert-safe probably makes concurrent execution
  harmless, but this hasn't been tested under real concurrency — don't
  assume it's proven safe, just probably-fine for the current
  single-instance deployment shape.

### 3.5 Surfacing state

- `GET /api/bootstrap/status` (public) —
  `{reinitializing, families: {name: {present, lastHealedAt, lastHealResult}}}`.
  `static/bootstrap-banner.js`, included on most top-level pages
  (`egeria-overview.html`, `egeria-operations.html`, `tech-catalog.html`,
  etc.), polls this and shows a banner while `reinitializing` is true.
- `GET /api/bootstrap/batches` (public) — every discovered batch with its
  current selection state, for the admin panel.
- `POST /api/bootstrap/batches/selection`,
  `POST /api/bootstrap/batches/{id}/run`,
  `POST /api/bootstrap/batches/run-all` — admin-only (same demo/freshstart
  admin gate `operations_handler.py` reuses for its connector/server
  actions), backing the **Data Initialization** panel: quickstart's
  `local-admin.html` (`/admin`), freshstart's `demo-admin.html` tab
  (`/admin`, freshstart didn't have an equivalent panel before this
  feature existed).

## 4. Quickstart vs. freshstart, at a glance

| | quickstart | freshstart |
|---|---|---|
| Admin page | `local-admin.html`, own page | `demo-admin.html`, "Data Initialization" tab |
| Postgres (`demo_auth`) | available | **not wired up at all** — no `DEMO_DB_*` vars, not on shared-infra's network |
| Hardcoded `BOOTSTRAP_FAMILIES` | empty — fully migrated to `_batch.json` | empty — never had quickstart's seed data to begin with |
| `advisor_lock_handler` / `demo_reset_handler` in `_lifespan` | present | absent (freshstart has no Advisor integration or DEMO_MODE) |

## 5. Files

- `pyegeria_handler.py` — `_bootstrap_runtime_defaults()`, `_lifespan`, router wiring.
- `bootstrap_monitor_handler.py` — canary detection, heal, scheduler, `/api/bootstrap/status`.
- `bootstrap_batches.py` — discovery, manifest parsing, ordering, selection state, `run_batch`/`run_all_enabled`.
- `bootstrap_admin_handler.py` — admin REST endpoints.
- `static/bootstrap-banner.js` — frontend "reinitializing" banner.
- `local-admin.html` (quickstart) / `demo-admin.html` (freshstart) — the Data Initialization admin UI.
